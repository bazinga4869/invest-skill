## 一、已修复 Bug（12 项）

### 1.1 sage-wiki CLI 在 cron/daily 环境找不到
- **问题**：`prepare_prompts.py` → `shared/sage_wiki.py` 调用 `sage-wiki`，但 cron 环境 PATH 极简（`/usr/bin:/bin`），`~/.local/bin` 不在其中 → `OSError: No such file or directory: 'sage-wiki'` → **所有股票 prompt 生成失败**（8/13-8/17 连续 5 天 daily 全挂的直接原因之一）。
- **根因**：`cron_trigger.sh` 有补 PATH，但 `daily_analysis.sh` 没有；`sage_wiki._cli()` 无回退逻辑。
- **修复**：`shared/sage_wiki.py::_cli()` 依次尝试 `SAGE_WIKI_CLI` 环境变量 → `shutil.which` → `~/.local/bin/sage-wiki`；`daily_analysis.sh` 补 `export PATH="$HOME/.npm-global/bin:$HOME/.local/bin:$PATH"`。
- **验证**：`env -i PATH=/usr/local/bin:/usr/bin:/bin` 下 CLI 正确解析并真实查询成功（5470 字符）。
- **建议加固**：所有脚本统一在入口做 PATH 归一（或 preflight 检查），避免逐脚本遗漏。

### 1.2 CAGR 门禁用四舍五入的亿元值重算，误杀小利润公司
- **问题**：`data_tools.py` 的 `validate_snapshot` 用 `annual_data[*].net_profit_yi`（四舍五入到 0.01 亿）重算 CAGR，与 `cmd_annual` 用原始元值计算的声明值比对，容差 0.15pp。小利润公司（亿元以下）舍入误差可达 1pp → 合法快照被 `annual.profit_cagr_*_pct 与年度序列重算不一致` 硬拒（复现：301359.SZ 偏差 0.93pp）。
- **修复**：`cmd_annual` 的 `annual_data` 条目新增 `revenue_yuan`/`net_profit_yuan` 原始字段；门禁优先用原始值重算，旧快照（无原始字段）回退 `*_yi`（与旧行为一致）。
- **验证**：301359.SZ `data_quality.status` 从 FAIL → WARN（仅剩合法警告）。

### 1.3 crontab 未设置 INVEST_SKILL_HOME（运行时迁移遗漏）

- **修复**：crontab 顶部加 `INVEST_SKILL_HOME=/home/bazinga/invest-harness/.invest-skill-runtime`、`INVEST_LOG_DIR=.../logs`（Vixie cron 顺序解析，env 必须在所有 invest-skill 任务之前）；两处 `>> logs/...` 重定向改绝对路径。备份：`/tmp/crontab.backup.20260817`。
- **建议加固**：`~/.config/invest-skill.env`（已被脚本 source）与 crontab 双源保持一致，或统一收敛到 env 文件。

### 1.4 cron_trigger 的 check_cron_done 评级模式缺 REDUCE/AVOID

- **建议加固**：评级词汇表收敛为单一常量（共享模块），避免多处硬编码漂移。

### 1.9 知识检索日志模板契约缺口（prompt 与校验器不一致）
- **问题**：`prepare_prompts.py` 的"知识检索日志"模板只渲染 `knowledge_paths[:3]`——sage 查询结果不足 3 条时表格只有 2 行，但文案写死"下表已预填 3 个本任务实际注入的页面"。模型无文件系统访问，无法可靠补出第 3 条**真实存在**的路径 → 编造路径（如 `raw/normalized/周期理论.md`、`wiki/books/投资心理学.md`）→ `collect_results.py` 的"少于 3 个真实存在的 wiki 页面"硬拒。**对只检索到 2 本书的专家，合格输出不存在（死锁），重试无法解决。**
- **修复**：模板预填不足 3 条时，用真实存在的方法论页（`method_path`、`supplemental_paths`）补齐；文案改为动态数字。
- **验证**：7 份 prompt 模板均预填 3 条、`_wiki_path_exists` 全真；重试批次 macro-cyclist 通过校验（66/WARN）。

### 1.11 prepare 超时/失败后 materialize/compile 子进程成孤儿

- **处理**：手工 kill 孤儿 + `runtime_guard.py release-run`。
- **建议加固**（⛔ 待 agent）：prepare 的超时/异常路径必须杀进程组（`os.killpg` / `start_new_session=True`）；report-wiki 的锁应记录持有者 PID 并支持陈旧锁回收。

## 二、未修复 / 需 skill agent 优化（⛔）

### 2.1 【核心】专家输出质量不稳定，7+1 门禁通过率极低
- **现象**（珀莱雅 603605.SH，8/17）：两批 14 份专家输出，仅 1 份（macro-cyclist，重试修复后）通过全部校验。
- **失败模式**：
  1. **未精确溯源数字**（最普遍）：模型写数字不紧跟 `[source: ...]`，或 source 路径在快照中不存在。
  2. **字段路径编造**：如写 `macro.gdp.latest.yoy_pct`，实际为 `macro.indicators.gdp.latest.yoy_pct`（数据完全正常）；`balance.total_assets_yi` 等真实字段也存在但 calc inputs 声明不全（`inputs: []`）→ calc 无法验证。
  3. **必检项证据路径不对**：checklist 条目（如"商誉 / 净资产"）要求证据路径，模型未引用 `balance.goodwill_ratio_pct`（字段存在）→ 报"证据超出专家数据域"。
  4. **结构化覆盖率不足**（76.9%/69.2%，要求 ≥80%）、个别缺必需章节（`## 详细分析`）。
- **根因**：deepseek-v4-flash 作为 worker 对严格格式契约的遵循度不稳定（8/11 成功时代的 prompt/门禁版本与现在不同）。同一 prompt 下模型输出批次间差异大（第一批 macro 部分路径正确，第二批整体崩坏，management-auditor 41 个数字仅 1 个被溯源）。
- **优化方向**：
  - prompt 内嵌**完整字段字典**（逐字段列出快照真实路径），并要求"路径必须从上方 JSON/证据卡片逐字复制，禁止推断"；
  - 提供**成功范例 few-shot**（如本次通过的 macro-cyclist 输出）；
  - 校验诊断**结构化回灌**：失败项（未溯源数字行号、缺失路径）作为下一轮输入，支持多轮修复（当前 `--retry` 仅一次、且模型看不到完整诊断）；
  - 评估换用更强/更稳的 worker 模型（claude）或提高 deepseek reasoning effort。

### 2.2 【核心】为什么分析过程需要人工审核——这本身是流程缺陷
- **现象**：8/12-8/17 连续 5 天 daily cron 全部静默失败；8/17 接管后，修复需要人工完成 12 处代码/配置修改；珀莱雅分析三批专家运行每次失败后都要人工判断下一步（重试？换后端？改契约？）。
- **分解为具体缺陷**：
  1. **失败无告警**：cron 失败只写日志文件，无任何推送（hermes 通道仅推送报告，不推送失败）。`activity.jsonl` 记录了 `status=failure` 但无消费方。→ 应有失败告警（hermes/邮件/桌面通知）。
  2. **诊断无反馈回路**：`collect_results.py` 的诊断信息（行号+原因）不进入 prompt；`--retry` 一次性且信息不完整。模型无法自我修复 → 人工介入。
  3. **契约不一致产生不可满足门禁**：prompt 模板与校验器各自维护规则（如 1.9 知识检索日志），不一致时**任何模型都过不了**，且现象像"模型质量差"，误导排查。→ 应共享单一契约源 + 生成后自检（prepare 后先跑校验器验证模板可满足）。
  4. **环境脆弱**：PATH 极简、配置分散（`~/.config/invest-skill.env`、crontab、`~/.codex/config.toml`、config.yaml）、脚本迁移残留（1.6）→ 一键 preflight 自检缺失。连续 5 天失败无人发现 = 无健康检查。
  5. **"无人值守"承诺未兑现**：cron_trigger 的 headless 自动裁决路径**从未成功跑通过**（8/17 前 02:00/04:30 cron 全部"未找到标的"或失败）；实际产出报告全部依赖交互式会话人工驱动。daily 产草稿后必须人工裁决，cron 无法闭环。
  6. **失败恢复路径依赖人工决策**：重试策略、换后端、改契约都需要人来判断；没有自动降级/自动重试策略。
- **期望形态**：分析流程应做到——失败自动重试（有界）→ 重试失败自动收集 diagnostics 并推送 → 契约问题在 prepare 阶段自检发现 → 专家阶段全自动 → 草稿自动裁决（headless）→ 发布。人工仅在最终报告审查时介入（且介入有明确依据）。

### 2.3 必检项（checklist）与快照字段契约不对齐
- **现象**：`expert_checklist.json` 条目（"商誉 / 净资产"、"国家基座分析（宏观定性）"、"股东回报记录"、"十分钟快速排除"等）被校验器判"证据超出专家数据域"或"证据路径不存在"。
- **原因**：checklist 期望的证据字段与当前数据快照字段/专家域映射未同步（快照有 `balance.goodwill_ratio_pct`、`macro.indicators.*`，但 checklist 或校验映射未对应）。
- **优化方向**：checklist 条目应带显式证据路径模板（如 `balance.goodwill_ratio_pct`），并在 prepare 阶段校验"该路径存在于快照"；专家域映射统一维护。

### 2.4 calc 校验与模型书写习惯的缺口
- **现象**：`[calc: ...; inputs: ...]` 的 inputs 声明不全（公式内嵌字段但 inputs 空）→ `evaluate_calculation` 返回 None → 硬拒。
- **优化方向**：校验器对"公式内嵌字段未在 inputs 声明"给出明确诊断（当前只报"公式或 inputs 无法验证"，无具体原因）；prompt 强调 inputs 必须完整列出公式内每个字段。

### 2.5 并发/孤儿进程与锁管理（承接 1.11）
- 多会话并发 materialize 时：单公司锁 OK（flock），但 prepare 被 kill 后孤儿持锁无回收机制；无跨会话协调（8/17 出现 3 个并行 materialize + 2 个 compile 同时跑，LLM 调用互相挤压）。
- **优化方向**：进程组终止；锁带 PID+心跳；并发放宽或排队；compile 进度可观测（当前看门狗只报"无进展"）。

### 2.6 analyzed.json 双轨记录
- **现状**：harness `data/analyzed.json`（人工/交互记录）与 invest-skill `auto_state.json`（cron 轮转）双轨；cron 成功后只更新 auto_state，不写 analyzed.json → 两条记录会分叉。
- **优化方向**：明确单一事实源或同步机制（cron 成功时同步写 analyzed.json）。
